# فایل `.env` و متغیرهای محیطی

## هدف درس
بعد از این درس می‌فهمی فایل `.env` چیست، چرا استفاده می‌شود، چه چیزهایی را نباید داخلش بگذاری، و در پروژهٔ SvelteKit / Node چطور متغیرهایی مثل `PORT` و `HOST` خوانده می‌شوند.

## پیش‌نیاز
- آشنایی اولیه با اجرای پروژه با `npm`
- دانستن اینکه پروژه روی سرور با Node اجرا می‌شود (مثل درس ۴)

---

## قدم ۱: متغیر محیطی چیست؟

وقتی برنامه اجرا می‌شود، سیستم‌عامل (یا ابزار اجرا مثل Vite / Node) می‌تواند چند **نام و مقدار** به برنامه بدهد؛ به این‌ها می‌گویند **environment variables** یا **متغیرهای محیطی**.

مثال ذهنی:

| نام | مقدار |
|-----|--------|
| `PORT` | `3000` |
| `HOST` | `0.0.0.0` |
| `NODE_ENV` | `production` |

برنامه به‌جای اینکه عدد پورت را سخت‌کد کند، می‌گوید: «از محیط بپرس پورت چیست؛ اگر نبود، پیش‌فرض ۳۰۰۰ را بگیر.»

در همین پروژه، داخل `server.js` دقیقاً همین کار انجام شده:

```js
const port = Number(process.env.PORT) || 3000;
const host = process.env.HOST || '0.0.0.0';
```

- `process.env` شیء مخصوص Node است که متغیرهای محیطی را نگه می‌دارد.
- اگر `PORT` تنظیم شده باشد، همان استفاده می‌شود.
- اگر نباشد، مقدار پیش‌فرض (`3000`) می‌آید.

---

## قدم ۲: فایل `.env` چیست؟

فایل `.env` یک فایل متنی ساده در ریشهٔ پروژه است که متغیرهای محیطی را به شکل `NAME=value` می‌نویسی تا موقع توسعه یا اجرا، برنامه آن‌ها را بخواند.

نمونه (محتوای مشابه `.env.example` همین پروژه):

```env
NODE_ENV=production
PORT=3000
HOST=0.0.0.0

# آدرس عمومی سایت (پشت nginx/proxy مهم است)
# ORIGIN=https://example.com
```

نکات نحو (syntax):

1. هر خط معمولاً یک متغیر است: `NAME=value`
2. فاصلهٔ اضافی دور `=` بهتر است نگذاری (`PORT = 3000` گاهی مشکل‌ساز می‌شود)
3. خط‌هایی که با `#` شروع می‌شوند **کامنت** هستند و اجرا نمی‌شوند
4. مقدار را معمولاً بدون فاصله و بدون نقل‌قول می‌نویسیم؛ اگر فاصله داشت می‌توانی داخل `"..."` بگذاری
5. این فایل کد JavaScript نیست؛ فقط جفت نام/مقدار است

---

## قدم ۳: چرا اصلاً `.env` لازم است؟

بدون `.env` مجبوری تنظیمات حساس یا وابسته به محیط را داخل کد بگذاری. آن کار چند مشکل دارد:

1. **محیط‌های مختلف فرق دارند**  
   روی لپ‌تاپت ممکن است `PORT=5173` باشد، روی سرور `PORT=3000`.
2. **رازها نباید داخل گیت بروند**  
   رمز دیتابیس، API key، توکن و امثال آن را اگر در کد commit کنی، همهٔ کسانی که به ریپو دسترسی دارند می‌بینند.
3. **تغییر تنظیمات بدون دست زدن به کد**  
   روی سرور فقط متغیر را عوض می‌کنی و سرویس را ری‌استارت می‌کنی؛ لازم نیست فایل سورس را ویرایش کنی.

خلاصه: `.env` جای نگهداری **تنظیمات وابسته به محیط** است، نه منطق برنامه.

---

## قدم ۴: تفاوت `.env` و `.env.example`

در پروژه‌های حرفه‌ای معمولاً دو چیز داری:

### `.env` (واقعی — خصوصی)
- مقادیر واقعی محیط تو (لوکال یا سرور)
- ممکن است شامل رمز و کلید باشد
- **نباید** به Git برود

### `.env.example` (نمونه — عمومی)
- فقط نام متغیرها و مقادیر نمونه / بی‌خطر
- راهنمای تیم است: «این متغیرها را باید تنظیم کنی»
- **باید** در ریپو بماند تا دیگران بدانند چه چیزی لازم است

در همین پروژه، `.gitignore` این‌طور نوشته شده:

```gitignore
# Env
.env
.env.*
!.env.example
!.env.test
```

معنی‌اش:

| الگو | معنی |
|------|------|
| `.env` | خود فایل env را ignore کن |
| `.env.*` | فایل‌هایی مثل `.env.local` و `.env.production` را هم ignore کن |
| `!.env.example` | استثنا: `.env.example` را ignore نکن (در گیت بماند) |
| `!.env.test` | استثنا: `.env.test` هم می‌تواند در گیت بماند |

پس جریان درست کار این است:

1. `.env.example` را از ریپو می‌گیری
2. کپی می‌کنی به `.env`
3. مقادیر واقعی را در `.env` پر می‌کنی
4. فقط `.env` روی ماشین خودت / سرور می‌ماند

---

## قدم ۵: انواع رایج فایل‌های env

بسته به ابزار، ممکن است چند فایل ببینی:

| فایل | نقش معمول |
|------|-----------|
| `.env` | تنظیمات پیش‌فرض محلی |
| `.env.local` | تنظیمات محلی شخصی (معمولاً اولویت بالاتر؛ نباید commit شود) |
| `.env.development` / `.env.production` | مخصوص حالت توسعه یا پروداکشن |
| `.env.example` | نمونهٔ بدون راز برای تیم |
| `.env.test` | مخصوص تست |

لازم نیست همه را داشته باشی. برای شروع همین پروژه، معمولاً کافی است:

- `.env.example` در گیت
- `.env` روی ماشین خودت (از روی example کپی‌شده)

## قدم ۶: چطور در Node خوانده می‌شود؟

در Node خام، متغیرها از طریق `process.env.NAME` در دسترس‌اند.

مثال از `server.js` همین پروژه:

```js
const port = Number(process.env.PORT) || 3000;
const host = process.env.HOST || '0.0.0.0';
```

توضیح بخش‌به‌بخش:

1. `process.env.PORT` → رشته است (مثلاً `"3000"`)، نه عدد
2. `Number(...)` آن را به عدد تبدیل می‌کند تا `app.listen` درست کار کند
3. `|| 3000` یعنی اگر مقدار نبود یا `0` / خالی بود، پیش‌فرض ۳۰۰۰

روی سرور واقعی، گاهی اصلاً فایل `.env` نمی‌گذاری و متغیر را مستقیم در سیستم یا PM2 تنظیم می‌کنی. نتیجه برای برنامه یکی است: `process.env.PORT` مقدار دارد.

مثال ذهنی با PM2 / سیستم:

```bash
PORT=3000 HOST=0.0.0.0 node server.js
```

اینجا فایل `.env` لازم نیست؛ مقدار از خط فرمان به محیط پاس داده شده.

---

## قدم ۷: در SvelteKit و Vite موضوع کمی خاص‌تر است

SvelteKit روی Vite ساخته شده. Vite فایل‌های `.env` را می‌خواند، ولی برای امنیت یک قانون مهم دارد:

### متغیرهای عمومی (می‌توانند به مرورگر بروند)
- باید با پیشوند `PUBLIC_` شروع شوند
- در کد کلاینت هم قابل استفاده هستند

مثال:

```env
PUBLIC_API_BASE=https://api.example.com
```

### متغیرهای خصوصی (فقط سمت سرور)
- بدون `PUBLIC_`
- نباید به مرورگر لو بروند (مثل رمز دیتابیس)

مثال:

```env
DATABASE_URL=postgres://user:pass@localhost/db
SECRET_KEY=super-secret
```

در SvelteKit معمولاً از ماژول‌های مخصوص env استفاده می‌کنی، نه اینکه همه‌جا خام `process.env` بنویسی:

| ماژول | کاربرد |
|--------|--------|
| `$env/static/private` | متغیرهای خصوصی که در build شناخته می‌شوند |
| `$env/static/public` | متغیرهای `PUBLIC_*` در build |
| `$env/dynamic/private` | خواندن پویا سمت سرور |
| `$env/dynamic/public` | خواندن پویا برای `PUBLIC_*` |

نکتهٔ امنیتی خیلی مهم:

> هر چیزی که با `PUBLIC_` بگذاری، فرض کن کاربر نهایی در مرورگر می‌تواند ببیند.  
> پس رمز، توکن، و کلید خصوصی را هرگز با `PUBLIC_` ننویس.

---

## قدم ۸: متغیرهای همین پروژه چه معنایی دارند؟

طبق `.env.example` فعلی:

```env
NODE_ENV=production
PORT=3000
HOST=0.0.0.0

# ORIGIN=https://example.com
```

| متغیر | معنی ساده |
|--------|-----------|
| `NODE_ENV` | حالت اجرا؛ معمولاً `development` یا `production` |
| `PORT` | پورتی که سرور روی آن گوش می‌دهد |
| `HOST` | آدرسی که سرور bind می‌شود؛ `0.0.0.0` یعنی از بیرون هم قابل دسترسی |
| `ORIGIN` | آدرس عمومی سایت (مثلاً پشت nginx). وقتی کامنت است یعنی فعلاً فعال نیست؛ در صورت نیاز خط را از حالت کامنت خارج کن |

`HOST=0.0.0.0` برای سرور واقعی رایج است، چون اگر فقط `127.0.0.1` باشد، معمولاً فقط از خود همان ماشین دیده می‌شود.

---

## قدم ۹: اشتباهات رایج

1. **commit کردن `.env` واقعی**  
   خطر لو رفتن رمز و کلید. همیشه در `.gitignore` باشد.

2. **گذاشتن مقدار واقعی داخل `.env.example`**  
   example باید بی‌خطر و آموزشی باشد، نه کپی از پروداکشن.

3. **فرض کردن که `.env` جادویی همه جا کار می‌کند**  
   در Node خام، گاهی باید خودت با ابزارهایی مثل `dotenv` لود کنی؛ در Vite/SvelteKit معمولاً برای حالت dev/build خودش مدیریت می‌شود. روی سرور پروداکشن اغلب متغیر را از سیستم / PM2 / Docker می‌دهی.

4. **استفاده از `PUBLIC_` برای رازها**  
   این یعنی عمداً آن را به کلاینت داده‌ای.

5. **فاصله و نقل‌قول بی‌دلیل**  
   `PORT=3000` درست‌تر از `PORT = "3000"` برای مبتدی است (مگر ابزارت صریحاً چیز دیگری بخواهد).

6. **فراموش کردن ری‌استارت**  
   بعد از تغییر `.env` معمولاً باید سرور dev یا پروسهٔ Node را دوباره اجرا کنی تا مقادیر جدید خوانده شوند.

---

## قدم ۱۰: جریان عملی پیشنهادی برای شاگرد

1. فایل `.env.example` را باز کن و ببین چه متغیرهایی تعریف شده‌اند.
2. در ریشهٔ پروژه یک فایل `.env` بساز (کپی از example).
3. مقادیر را برای محیط خودت تنظیم کن (مثلاً `PORT=3000`).
4. مطمئن شو `.env` در `.gitignore` هست و با `git status` دیده نمی‌شود.
5. برنامه را اجرا کن و ببین `server.js` همان پورت را استفاده می‌کند.
6. عمداً `PORT` را عوض کن، سرور را ری‌استارت کن، و نتیجه را ببین.

اگر متغیر را حذف کنی و کد پیش‌فرض داشته باشد (مثل `|| 3000`)، برنامه نباید بشکند؛ فقط به پیش‌فرض برمی‌گردد.

---

## جمع‌بندی

- `.env` فایل متنی برای تنظیمات وابسته به محیط است (`NAME=value`).
- هدفش جدا کردن تنظیمات (و رازها) از کد است.
- `.env` خصوصی است و نباید commit شود؛ `.env.example` عمومی است و باید در ریپو بماند.
- در Node با `process.env` خوانده می‌شود؛ در همین پروژه `PORT` و `HOST` در `server.js` استفاده شده‌اند.
- در SvelteKit/Vite، فقط متغیرهای `PUBLIC_*` اجازه دارند به مرورگر برسند؛ بقیه سمت سرور می‌مانند.
- روی سرور واقعی، منبع حقیقت اغلب خود محیط سیستم / PM2 / Docker است، نه لزوماً فایل `.env` داخل ریپو.

## تمرین

1. از روی `.env.example` یک `.env` بساز و `PORT` را به عدد دیگری (مثلاً `4000`) تغییر بده؛ سپس با اجرای سرور ببین آیا روی همان پورت بالا می‌آید.
2. توضیح بده چرا `.env` در `.gitignore` است ولی `.env.example` با `!` استثنا شده.
3. یک متغیر فرضی مثل `SECRET_API_KEY` را در نظر بگیر و بنویس چرا نباید آن را به شکل `PUBLIC_SECRET_API_KEY` تعریف کنی.
