# درس ۱۵: جریان return کردن داده از سرور تا فرانت

## هدف درس
بعد از این درس می‌توانی مسیر یک مقدار را از لحظهٔ `return` در سرور تا رسیدن به UI در مرورگر قدم‌به‌قدم توضیح بدهی: چه چیزی خصوصی می‌ماند، چه چیزی سریالایز می‌شود، چطور داخل HTML یا پاسخ ناوبری می‌آید، و در `+page.svelte` چگونه به‌صورت `data` خوانده می‌شود.

## پیش‌نیاز
- درس ۱۱ (hooks و `locals`)
- درس ۱۴ (load functions)
- درک خیلی ساده از SSR (اول سرور HTML می‌سازد، بعد مرورگر hydrate می‌کند)

---

## قدم ۱: یک جملهٔ مرکزی

در SvelteKit دادهٔ صفحه این مسیر را می‌رود:

```text
منبع (DB / API / کوکی)
  → کد سرور (hooks / load.server)
  → return یک شیء سادهٔ قابل‌انتقال
  → سریالایز (devalue)
  → ارسال به مرورگر (داخل SSR یا درخواست ناوبری)
  → deserialize
  → propِ data در +layout / +page
  → رندر UI
```

تا وقتی چیزی را **return نکنی** (یا در `data` صفحه قرار نگیرد)، فرانت آن را نمی‌بیند — حتی اگر روی سرور در `locals` باشد.

---

## قدم ۲: دو لایهٔ داده روی سرور — قاطی نکن

| لایه | کجاست | به فرانت می‌رسد؟ |
|------|--------|-------------------|
| `event.locals` | `hooks.server` و load/endpoint سرور | **خیر**، مگر خودت در `return` بیاوری |
| `return` از `load` | `+page.server.ts` / `+layout.server.ts` | **بله** (اگر قابل سریالایز باشد) |
| state داخل کامپوننت | `$state` در `.svelte` | مال همان کلاینت/hydrate است؛ از DB مستقیم نیست |

مثال خطرناک:

```ts
// hooks.server.ts
event.locals.user = await getUser(session);
event.locals.dbPassword = '...'; // هرگز

// +layout.server.ts
return {
	user: event.locals.user,           // OK اگر فیلدهای امن باشد
	// dbPassword: event.locals.dbPassword  // فاجعه — می‌رود سمت کاربر
};
```

قانون طلایی:

> **سرور می‌تواند همه چیز را بداند؛ فرانت فقط آنچه return شده را می‌بیند.**

---

## قدم ۳: نقطهٔ شروع — `return` در `load` سرور

```ts
// src/routes/blog/[slug]/+page.server.ts
import type { PageServerLoad } from './$types';
import { error } from '@sveltejs/kit';

export const load: PageServerLoad = async ({ params, locals }) => {
	const post = await getPostFromDb(params.slug);
	if (!post) error(404, 'پیدا نشد');

	return {
		post: {
			title: post.title,
			body: post.body
		},
		viewerName: locals.user?.name ?? null
	};
};
```

این `return` هنوز «روی صفحه» نیست؛ فقط می‌گوید:

> این شیء را برای این درخواست به‌عنوان دادهٔ صفحه آماده کن.

Kit بعداً آن را با خروجی layoutها ادغام می‌کند و به سمت رندر/انتقال می‌برد.

---

## قدم ۴: ادغام لایه‌ها قبل از خروج از سرور

برای URL مثل `/blog/hello`:

```text
+layout.server.ts (ریشه)   return { siteName: 'کلاس' }
+layout.server.ts (blog)   return { posts: [...] }
+page.server.ts            return { post: {...}, viewerName }
```

نتیجهٔ تقریبی برای صفحه:

```ts
{
	siteName: 'کلاس',
	posts: [ /* ... */ ],
	post: { title, body },
	viewerName: 'سجاد'
}
```

اگر کلید تکراری باشد، مقدار سطح پایین‌تر (آخری) برنده است.

تا اینجا همه چیز هنوز در حافظهٔ سرور است.

---

## قدم ۵: مرز سریالایز — پل سرور ↔ فرانت

دادهٔ `load` سرور باید از شبکه رد شود. SvelteKit با **devalue** آن را کد می‌کند؛ تقریباً:

- انواع JSON: object, array, string, number, boolean, null  
- به‌علاوه چیزهایی مثل `Date`, `Map`, `Set`, `BigInt`, `RegExp`  
- و حتی `Promise` (برای streaming)  

نمی‌توانی به‌سادگی برگردانی:

- اتصال باز دیتابیس  
- تابع  
- کلاس دلخواه بدون `transport` hook  
- مقدار دایره‌ای غیرپشتیبانی‌شده به شکل غلط  

پس «return کردن از سرور» یعنی:

> تبدیل به داده‌ای که **قابل کپی شدن روی سیم** است.

اگر نوع سفارشی لازم داری → `transport` در `hooks.ts` (درس ۱۱).

---

## قدم ۶: مسیر الف — بازدید اول (SSR)

وقتی کاربر آدرس را مستقیم باز می‌کند یا رفرش می‌کند:

```text
1) درخواست HTML به سرور
2) hooks.handle →locals
3) loadهای سرور اجرا و return می‌شوند
4) (اگر باشد) load یونیورسال روی سرور هم اجرا می‌شود
5) Svelte کامپوننت‌ها را با همان data روی سرور رندر می‌کند
6) HTML آماده می‌شود؛ data لازم برای hydrate هم همراه صفحه می‌آید
7) مرورگر HTML را نشان می‌دهد (حتی قبل از اجرای کامل JS)
8) JS لود می‌شود → hydrate → همان data به props وصل می‌شود
```

تصویر ساده:

```text
[Server]
 locals → load.return → data
              │
              ├─► رندر HTML: <h1>عنوان پست</h1>
              │
              └─► payload داده برای hydrate
                    │
                    ▼
                 [Browser]
              data روی +page.svelte
```

فایده: کاربر زود محتوا را می‌بیند؛ SEO هم متن واقعی دارد.

---

## قدم ۷: مسیر ب — ناوبری کلاینتی (`<a href>`)

وقتی داخل اپ روی لینک کلیک می‌کند:

```text
1) مرورگر درخواست کامل سند نمی‌دهد (معمولاً)
2) Kit از سرور دادهٔ route جدید را می‌گیرد (JSON-مانند / پروتکل داخلی Kit)
3) load سرور روی سرور دوباره اجرا و return می‌شود
4) داده deserialize می‌شود
5) فقط صفحه/layoutهای لازم با data جدید عوض می‌شوند
```

اینجا هم مبدأ همان `return` سرور است؛ فقط بسته‌بندی حمل فرق دارد:

| بازدید اول | ناوبری بعدی |
|------------|-------------|
| HTML + دادهٔ همراه | بیشتر تمرکز روی انتقال data |
| رندر اول روی سرور | رندر صفحهٔ جدید روی کلاینت با data تازه‌وارد |

در هر دو حالت، قرارداد برنامه‌نویس یکی است: **`return` از load → `data` در UI**.

---

## قدم ۸: رسیدن به فرانت — خواندن در `.svelte`

```svelte
<script lang="ts">
	import type { PageProps } from './$types';

	let { data }: PageProps = $props();
</script>

<h1>{data.post.title}</h1>
<p>بیننده: {data.viewerName}</p>
```

اینجا دیگر سرور اجرا نمی‌شود؛ فقط داری مقداری را نشان می‌دهی که سفرش را کرده.

در layout:

```svelte
let { data, children }: LayoutProps = $props();
```

و اگر والد به دادهٔ صفحه نیاز داشت:

```svelte
import { page } from '$app/state';
// page.data.title
```

| راه خواندن | معنی |
|------------|------|
| `data` از `$props()` | دادهٔ این layout/صفحه (+ ارث از والدها طبق قواعد Kit) |
| `page.data` | نمای ترکیبی مسیر فعلی؛ مفید در layout ریشه برای title و … |

---

## قدم ۹: نقش `+page.ts` یونیورسال در وسط راه

گاهی زنجیره این است:

```text
+page.server.ts  return { raw: ... }
        │
        ▼
+page.ts  load({ data })  →  return { view: transform(data.raw) }
        │
        ▼
+page.svelte  data.view
```

یعنی سرور خام را می‌دهد؛ لایهٔ یونیورسال شکل نهایی برای UI را می‌سازد.  
خروجی نهایی که صفحه می‌بیند معمولاً همان return یونیورسال است.

اگر فقط `.server.ts` داشته باشی، همان خروجی مستقیماً به `data` صفحه می‌رسد.

---

## قدم ۱۰: چه چیزهایی عمداً «نیمه‌راه» می‌مانند؟

### ۱) `locals`
فقط روی سرور برای این درخواست زنده است. فرانت نمی‌بیند مگر در `return`.

### ۲) متغیر محلی داخل `load`
```ts
const secret = process.env.SECRET;
const post = await db.getPost(slug);
return { post }; // secret نمی‌رود
```

### ۳) پاسخ `+server.ts` وقتی از کلاینت `fetch` می‌زنی
مسیر جداست: endpoint → `Response` → کلاینت.  
این هم «از سرور به فرانت» است، ولی از لولهٔ `data` صفحه رد نمی‌شود مگر در `load` همان را `fetch` کنی و return کنی.

```text
مسیر A: load.server return → data صفحه
مسیر B: +server.ts → fetch از مرورگر → JSON در کامپوننت
```

برای رندر اول صفحه معمولاً مسیر A درست‌تر است.

---

## قدم ۱۱: یک داستان کامل با اعداد مشخص

فرض: کاربر لاگین‌شده `/blog/hello` را باز می‌کند.

```ts
// hooks.server.ts
event.locals.user = { id: 'u1', name: 'سجاد', role: 'admin' };
```

```ts
// +page.server.ts
return {
	post: { title: 'سلام', body: '...' },
	viewer: { name: locals.user.name } // فقط name؛ نه role اگر لازم نیست
};
```

```svelte
<!-- +page.svelte -->
<h1>{data.post.title}</h1>
<p>{data.viewer.name}</p>
```

سفر `title`:

```text
ردیف DB "سلام"
  → شیء post در حافظهٔ Node
  → return { post: { title: 'سلام', ... } }
  → serialize
  → HTML یا payload ناوبری
  → data.post.title در مرورگر
  → متن داخل <h1>
```

سفر `role: 'admin'`:

```text
locals.user.role روی سرور هست
  → در return نیامد
  → در فرانت وجود ندارد
```

این همان کنترل امنیتی مرز داده است.

---

## قدم ۱۲: بعد از رسیدن به فرانت چه می‌شود؟

وقتی `data` آمد:

1. می‌توانی مستقیم در markup نشانش بدهی  
2. می‌توانی از رویش `$derived` بسازی  
3. می‌توانی کپی به `$state` محلی برای ویرایش فرم بگیری (کپی ≠ منبع سرور)  
4. برای تازه کردن از سرور دوباره باید `invalidate` / ناوبری / action انجام شود — عوض کردن `data` محلی دیتابیس را عوض نمی‌کند  

`data` ورودی از سرور است؛ «منبع حقیقت» بعد از hydrate همچنان با رفرش مجدد load تازه می‌شود.

## قدم ۱۳: نمودار جمع‌بندی یک‌صفحه‌ای

```text
┌──────────── Server ────────────┐
│  cookies / DB / env خصوصی      │
│           │                    │
│           ▼                    │
│     hooks → locals             │
│           │                    │
│           ▼                    │
│   load.server → return {...}   │
│           │                    │
│     (اختیاری) load.ts          │
│           │                    │
│      merge با layout data      │
│           │                    │
│        serialize               │
└───────────┼────────────────────┘
            │  شبکه
            ▼
┌──────────── Browser ───────────┐
│      deserialize               │
│           │                    │
│     data / page.data           │
│           │                    │
│   +layout.svelte / +page.svelte│
│           │                    │
│         DOM / UI               │
└────────────────────────────────┘
```

## قدم ۱۴: اشتباهات رایج در همین جریان

1. **فرض اینکه `locals` خودکار به کلاینت می‌رود**  
2. **return کردن کل ردیف DB با فیلدهای حساس**  
3. **return کردن تابع یا اتصال DB**  
4. **تغییر `data` در کلاینت و انتظار ذخیره روی سرور**  
5. **گم کردن تفاوت SSR اول با ناوبری بعدی** (هر دو از return می‌آیند، حمل فرق دارد)  
6. **نشان دادن داده فقط با `fetch` در `$effect` و دور زدن این لوله** — SSR خالی می‌ماند  

---

## قدم ۱۵: چک‌لیست قبل از هر `return` سرور

از خودت بپرس:

1. آیا کاربر مجاز است این فیلد را ببیند؟  
2. آیا مقدار قابل سریالایز است؟  
3. آیا فقط همان چیزی که UI لازم دارد را برمی‌گردانم؟  
4. آیا نام فیلدها با چیزی که در `+page.svelte` می‌خوانم یکی است؟  
5. آیا دادهٔ مشترک باید از layout بیاید نه تکرار در هر صفحه؟  

اگر این پنج تا سبز بود، مسیر سرور→فرانت تمیز است.

---

## جمع‌بندی

- فرانت فقط دادهٔ **return‌شده از `load`** (و مسیرهای صریح مثل `fetch` به `+server`) را می‌بیند.  
- `locals` و متغیرهای سرور به‌خودی‌خود عبور نمی‌کنند.  
- بعد از `return`، Kit داده را ادغام، سریالایز، و در SSR یا ناوبری به مرورگر می‌رساند.  
- در UI با `data` یا `page.data` می‌خوانی.  
- مرز سریالایز همان مرز امنیتی و طراحی API صفحه است: هرچه return کنی، فرض کن کاربر می‌تواند ببیند.  
- پروژهٔ فعلی هنوز این لوله را فعال نکرده؛ به‌محض افزودن `+page.server.ts` و خواندن `data` در صفحه، همین جریان زنده می‌شود.

## تمرین

1. برای یک پست فرضی بنویس کدام فیلدها در `locals` می‌مانند، کدام در `return` می‌آیند، و کدام در `+page.svelte` چاپ می‌شوند.  
2. توضیح بده چرا `return { user: locals.user }` اگر `user` فیلد `passwordHash` داشته باشد خطرناک است و شکل امن‌تر return چیست.  
3. فرق رسیدن داده در «رفرش کامل صفحه» با «کلیک روی لینک داخلی» را در سه جمله بگو — با تأکید بر اینکه مبدأ هر دو همان `return` است.  
4. این جمله را کامل کن: «اگر در سرور حساب کردم ولی در UI `undefined` است، احتمالاً …»
